Roofline Model
屋顶线模型

Roofline Model 回答一个最本质的问题：在硬件峰值算力 π 和显存带宽 β 给定的前提下，一个算术强度为 I 的 kernel 理论上最多能跑多快？它把所有性能瓶颈归一到两条线——内存带宽斜线和峰值算力水平线——组成的"屋顶"。_kernel 落在斜线段就是 memory-bound，落在水平段就是 compute-bound。_

为什么它重要：在动手优化前先用 Roofline 判断方向，能避免"无脑加 Tensor Core 但 kernel 其实卡在 HBM 带宽上"这类错误。它是 CUDA/HPC 性能分析的第一性工具，也是 NVIDIA、DeepSeek、字节等公司 LLM-infrastructure 面试的高频考点。
典型 Roofline（log-log） 横轴 AI ｜ 纵轴 Performance

1核心概念：三个量 + 一个 min

把 Roofline 想成三件事：硬件能提供什么、kernel 需要什么、两者怎么耦合。

π Peak Compute

GPU 单位时间能完成的最多浮点运算数，单位 FLOP/s。和 dtype 强相关：FP64 < FP32 < FP16 < Tensor Core (BF16/FP16/FP8)。例如 H100 SXM5：FP64 34 TFLOPs，FP32 67 TFLOPs，FP16 Tensor Core 989 TFLOPs，FP8 1979 TFLOPs。

β Peak Memory Bandwidth

GPU 单位时间从显存搬运的最多字节数，单位 Byte/s。HBM3e 比 HBM2e 快很多：H100 SXM5 是 3.35 TB/s，H200 是 4.8 TB/s，B200 是 8 TB/s。注意这是理论峰值，实测通常打 80~90%。

I Arithmetic Intensity

kernel 每从内存搬运 1 Byte 能做多少次浮点运算：_I = FLOPs / Bytes_。注意分母是实际触达 DRAM 的字节数（cache 命中的不算），不是程序申请的内存大小。

核心公式 Attainable Performance

# 内存带宽能撑起的性能上限： Pmem(I) = β · I # 计算单元能撑起的性能上限： Pcomp(I) = π # Roofline 取两者最小值： Pattain(I) = min( β · I , π )

为什么是 min？因为 GPU 是流水线机器，计算和访存同时进行。_P = FLOP/s_ 必须同时满足"算得过来"和"喂得过来"。任一环节供应不足，整体就卡在那个环节。带宽斜线 P = β·I 描述"喂得过来"的极限，计算水平线 P = π 描述"算得过来"的极限。两者交点叫 Ridge Point。

I* Ridge Point：分水岭

# 令 β·I = π 解出 I： I* = π / β # 单位 FLOPs/Byte

Ridge Point 是 memory-bound 和 compute-bound 的分水岭。以 H100 SXM5 (FP32) 为例：I* = 67 / 3.35 ≈ 20 FLOPs/Byte。AI < 20 的 kernel 一定 memory-bound；AI > 20 才有机会 compute-bound。注意不同 dtype 的 π 不同，ridge point 也不同：FP16 Tensor Core 的 I* ≈ 989/3.35 ≈ 295，所以 Tensor Core kernel 必须 AI 极高才可能 compute-bound。

2为什么 log-log 图上斜率是 1？

这是 Roofline 视觉化最容易被忽略、但面试常问的细节。

线性轴 不直观

如果直接画 P = β·I，斜率为 β 的直线。但 GPU 上 AI 跨度极大：elementwise ~0.2，GEMM N=4096 ~680。线性轴下小 AI 的 kernel 全挤在原点附近看不清。

log-log 斜率 1

对两边取 log：log P = log β + log I。在 log-log 图上这是一条斜率恒为 1的直线，与 β 无关——β 只决定截距。换硬件时 β 变大，斜线整体上移，ridge point 右移。

关键推论：log-log 图上 log P = log π 是水平线，log P = log β + log I 是 45° 斜线。两线交点即 ridge point。_把一个 kernel 放进图中，它一定落在屋顶线下方——离屋顶越远，说明优化空间越大_。

4常见 Kernel 的 AI 速查表

面试常考"某 kernel 是 memory-bound 还是 compute-bound"。下面是手算 AI 的标准方法。

手算公式 AI = 总 FLOPs / 总 DRAM Bytes

# 分子：kernel 实际执行的浮点运算次数 FLOPs = (循环次数) × (每次迭代的浮点运算数) # 分母：从 HBM 搬运的字节数（命中 cache 的不算） Bytes = Σ (每个 tensor 的元素数 × dtype 字节数) # 仅首次未命中部分 I = FLOPs / Bytes
Kernel FLOPs DRAM Bytes (FP32) AI (FP32) 分类 典型优化方向
Elementwise (axpy: y = αx+y) 2N 12N (读 x,y,写 y) 0.17 Memory 合并访问、vectorized load、kernel fusion
Reduction (sum: Σxᵢ) N 4N (读 x, 写 1 个标量可忽略) 0.25 Memory tree reduction、warp shuffle、避免 bank conflict
LayerNorm (over D) ~5D ~12 (读 x 2 趟: mean+var+norm, 写 y) ~0.4 Memory online 归一化、kernel fusion、register tiling
Softmax (over D) ~3D ~12 (3 趟扫描) ~0.25 Memory online softmax (Flash-1)、shared memory
3D Stencil (7-pt) 7N ~32N (含 halo) ~0.22 Memory cache blocking、shared memory tiling、time skewing
GEMM N=N (C=A·B, FP32) 2N³ ~12N² (A,B 各读 N², C 写 N²; 复用 N 次) N/6 Memory (N=64) shared memory tiling → register tiling → Tensor Core
GEMM N=4096 2·4096³ ~12·4096² ~683 Compute Tensor Core、pipeline、warp tile
Attention (naive, N=d) ~5N²d ~16N² (Q,K,V,O 4 个 N×d) ~5d/16 Memory (d=64) FlashAttention (tiling + online softmax)
FlashAttention-2 ~5N²d ~16N² (但 HBM 流量降到理论下限) ~5d/16 Balanced 已接近 roofline; 进一步靠 dtype + 算子融合
关键洞察：从 AI 表能直接看出算法分类——O(N) 计算配 O(N) 访存的 kernel（elementwise/reduction/layernorm）几乎一定 memory-bound；O(N³) 计算配 O(N²) 访存的 GEMM 在 N 足够大时一定 compute-bound。Transformer 推理的 prefill 阶段（GEMM 为主）通常 compute-bound；decode 阶段（逐 token、KV cache 读多算少）几乎总是 memory-bound——这是 LLM 推理系统设计的核心约束。

5多层级 Roofline：缓存也有屋顶

真实 GPU 不是"CPU↔HBM"两点结构，而是 L1→L2→HBM 多级。每级都有带宽上限，对应一条不同的斜线。

单层 Roofline 仅 HBM

最简单的 Roofline 只画 HBM 带宽斜线。它假设所有数据都从 HBM 搬。但真实 kernel 会命中 L1/L2 cache，实际 DRAM 流量比"申请内存字节数"小，AI 反而更高。

多层 Roofline Hierarchical

对每一级 cache 画一条带宽斜线：L1 斜线最高、L2 次之、HBM 最低。kernel 实际落点取决于数据复用模式：tile 内复用命中 L1，跨 tile 命中 L2，跨 iteration 才回 HBM。

CEIL Compute 也有多条

水平线也不止一条：FP64/FP32/FP16/BF16/FP8 各有自己的 π，Tensor Core 的 π 远高于 CUDA Core。还会按指令类型分（FMA vs MULT vs SFU）。NVIDIA 工具里把这种"分类型的上限"叫 ceil，把多层 roofline 叫 hierarchical roofline。

# 完整 Roofline 应取所有 ceil 的最小值： Pattain(I) = min( πFMA, βHBM·I, βL2·IL2, βL1·IL1, ... )
实战要点：_ncu_ (Nsight Compute) 给出的 roofline 默认是 HBM-only。要看 L2 命中后的真实 AI，需要看 sm__inst_executed_pipe_* 等指标，并对比 dram__bytes_read 与 lts__t_bytes（L2 流量）。这是高级 kernel 优化必经一步。

6如何实测 AI 和 Achieved Performance

理论 AI 是手算的；实战必须用 profiler 实测，否则优化方向可能完全错。

Step 1 ncu 命令行

ncu --set roofline \\ --target-processes all \\ -k "regex:your_kernel" \\ -o profile.ncu-rep \\ ./your_app

--set roofline 会自动收集绘制 roofline 所需的所有指标：每个 kernel 的 achieved FLOP/s、DRAM bytes、L2 bytes、指令分布等。

Step 2 关键指标

  • sm__throughput.avg.pct_of_peak_sustained_elapsed — 计算 SM 占用率
  • dram__throughput.avg.pct_of_peak_sustained_elapsed — HBM 带宽占用率
  • sm__inst_executed_pipe_tensor_op_hmma.sum — Tensor Core 指令数
  • dram__bytes.sum — 实际 DRAM 流量（用来算真实 AI）
  • smsp__inst_executed.sum — 总指令数

Step 3 在 ncu-rep 里读图

ncu-rep 的 roofline 视图会画出每个 kernel 的实测点叠在屋顶下。点的颜色表示瓶颈类型（绿=memory-bound、紫=compute-bound、黄=latency-bound）；点到屋顶的距离就是优化空间。如果点既不在斜线也不在水平线附近，说明latency-bound——这是单层 roofline 看不到的盲区，需要看 stall reasons。

常见坑：(1) 手算 AI 用"申请内存大小"作分母，但 cache 命中后真实 DRAM 流量更小，实测 AI 更高；(2) 用 FP32 算 FLOP/s 但 kernel 实际跑 Tensor Core，π 估计错位；(3) Multi-kernel launch 场景下 ncu 默认只 profile 第一个，需要 --launch-count N 或指定 --launch-skip。

7Roofline 的局限性

面试官常追问："什么时候 Roofline 失效？"——以下都是。

1 Latency-bound 不可见

Roofline 只看吞吐量（throughput），不看延迟（latency）。如果 kernel 中每个 warp 只能跑少量指令且依赖链长（如 scan、递归、串行依赖），即使带宽和算力都没满，性能也上不去。这叫 latency-bound，需要看 smsp__warp_issue_stalled_* stall reasons。

2 Occupancy 不代表性能

高 occupancy 不等于高性能。寄存器压力大、指令级并行（ILP）差的 kernel 即使 occupancy 100% 也可能跑不到屋顶。不要把 occupancy 当优化目标，把它当诊断指标。

3 理论 π ≠ Achievable π

规格书的 π 是 FMA 全速的极限值。真实 kernel 有指令混合（FMA/MUL/SFU/INT 比例），实际 achievable π 通常只有规格值的 70~90%。建议用实测峰值（如 cutlass benchmark）替代规格值画屋顶。

4 单一 dtype 假设

真实 kernel 经常混合 dtype（如 layernorm 中 FP32 accumulator + FP16 输入）。单一 π 画不出准确屋顶，需要按指令类型分别取 ceil。

5 忽略非算术单元

SFU（特殊函数 sin/cos/exp）、LSU（load/store unit）、copy engine 都不在 roofline 里。_exp_ 密集的 kernel 可能卡在 SFU 而不是 FMA。需要看 pipe-level 指标。

6 系统级瓶颈不可见

Roofline 是单 kernel模型。多 kernel 之间的 launch overhead、CPU-GPU 同步、PCIe/NVLink 数据传输、KV cache 拷贝、stream 串行化等系统级瓶颈，需要 Nsight Systems 而非 Nsight Compute。

8实战案例：GEMM 优化路径

从 naive GEMM 到 Tensor Core，看每一步在 roofline 上的位置如何变化（N=4096 FP32, H100 SXM5）。

版本 实现 实测 AI 实测 P Roofline 上位置 下一步瓶颈
v1 Naive 每线程算一个 C[i,j]，A/B 重复读 N 次 0.17 (DRAM 真实流量≈12N³) ~0.5 TFLOP/s 远离斜线（既没吃满带宽也没算满） 访存浪费 → 引入 tiling
v2 Shared Memory Tiling 32×32 tile 进 shared memory，block 内复用 ~8 ~25 TFLOP/s 斜线下方，离 ridge I*=20 还有距离 仍 memory-bound → 增大 tile
v3 Register Tiling 每线程算 8×8 micro-tile，寄存器累积 ~50 ~50 TFLOP/s 跨过 ridge，但低于 π=67 开始 compute-bound → Tensor Core
v4 Tensor Core (BF16) 用 wmma / mma，BF16 输入 FP32 累加 ~200 (BF16 bytes 减半) ~600 TFLOP/s BF16 屋顶 π=989 下方 60% kernel 调度 / pipeline / L2
v5 Cutlass-style double buffer + async copy + warp specialization ~280 ~850 TFLOP/s 接近 BF16 屋顶 86% 已接近理论极限
关键模式：每次 AI 跳跃都是数据复用带来的（tiled in shared memory → tiled in register → tensor core fragment）；每次 P 跳跃都是切到更高 π 的 ceil（CUDA Core → Tensor Core）。这就是为什么 LLM kernel 优化本质是"沿着 roofline 爬"——先把 AI 推过 ridge，再切到更高 π 的 ceil。

面试要点速记

以下问题是 NVIDIA / DeepSeek / 字节等公司 LLM-infra 面试的高频考点：

  • 什么是 Roofline Model？用 min(π, β·I) 给出 kernel 理论性能上限。π 是峰值算力，β 是显存带宽，I 是算术强度。
  • Ridge Point 怎么算？I* = π/β。AI 小于 I* 是 memory-bound，大于 I* 才可能 compute-bound。不同 dtype 的 π 不同，ridge point 也不同。
  • 如何判断 kernel 是 memory-bound？实测 AI < I*，或 ncu 显示 dram__throughput 接近 100% 而 sm__throughput 低。
  • 点离屋顶很远说明什么？不是带宽或算力瓶颈，可能是 latency-bound、occupancy 不足、寄存器溢出、bank conflict、同步开销。看 stall reasons。
  • 如何提高 AI？shared memory tiling、register tiling、kernel fusion（避免中间结果写回 HBM）、改变算法（如 FlashAttention 的 online softmax）。
  • Roofline 的局限？不看 latency、不区分指令类型（默认 FMA）、不显示 cache 层级（需 hierarchical roofline）、不反映系统级瓶颈（需 Nsight Systems）。
  • LLM 推理为什么 decode 几乎总是 memory-bound？每生成 1 token 需读 KV cache（O(N·d) bytes）但只做 O(d²) 计算，AI 极低。Prefill 是批量 GEMM，AI 高，通常 compute-bound。这是连续批处理 / paged attention / chunked prefill 等系统设计的根本原因。
  • FlashAttention 为什么快？不是降低了 FLOPs，而是通过 tiling + online softmax 把 attention 的 HBM 流量从 O(N²d) 降到 O(N²)，AI 提升数倍，把 memory-bound 的 kernel 推到接近 ridge。这是用算法换 AI 的经典案例。
